# Video modules and ownership — current implementation (2026-11-18)

This document is an **implementation-facing map**, not a new architecture proposal. Confirm script references against the current main and use `npm run architecture:report -- --json` for code-derived dependency candidates.

## Top-level entry and execution order

- `video.html` is a **Home SPA route**, not the standalone player; `home-profile-spa.js` creates `VideoListRouteFactory` from `video-list-route.js` after `video-list-template.js`. Only the route invokes `MangaReaderVideoLibrary.init(mediaAccess)`.
- The video route awaits the VPN gate and `video-library.css` and then loads `video-data.js`, shared pagination events, `video-library-pagination.js`, thumbnail cache/renderer, `video-card.js`, custom property definitions/store, `video-library-view.js`, and finally `video-library.js`. Only after these resolve does it call `init()`; detaching invalidates in-flight starts. Extra routing/thumbnail bridges are loaded only when protected data is readable.
- `video-edit.html`, `video-player.html`, `video-properties.html`, `video-shorts.html`, `video-virtual-editor.html`, `video-virtual-player.html` are separate documents. Their listed scripts must remain in their actual HTML load order. They have their own page controller, but **must not initialize the SPA video list**.
- `media-access-gate.js` supplies access decisions, `vault-payload.js` supplies the protected snapshot schema, and `vault-session.js` implements encrypted syncing/CAS/tombstones. These are shared infrastructure, not modules to duplicate per page.

## Data ownership and trust boundary

- `mangaReaderVideos` is the canonical list of video base records; metadata is `mangaReaderVideoMeta`; folders are `mangaReaderVideoFolders`. Custom property values are separately managed by `video-custom-property-store.js`. The **protected payload key list** belongs to `vault-payload.js`.
- Several entrypoints currently read or write the same protected video records (`video-library.js`, `video-edit-page.js`, `video-routing-fix.js`, `video-player-page.js`, virtual publish and Shorts). This is **remaining coupling**, not a license to introduce a second database. Future consolidation must preserve pending markers before local writes, deletion journaling/tombstones, guest handling, VPN gating and three-way Vault sync.
- `MangaReaderVideoData.findDuplicateVideoUrls` identifies eligible duplicate URL groups while excluding published edits. `planVideoUrlConsolidation` derives the four resulting collections and removed IDs from supplied snapshots. `video-library.js` coordinates the guarded batch across the four stores, using the shared batch writer and Vault journal. Guest writes use scoped browser storage. The record formats, pending marker, encryption, CAS, and tombstone paths retain their existing contracts.
- The View observes the list state for rendering but never mutates state or storage. It receives explicit event callbacks. `video-library.js` owns updated favorites, selection sets, expansions and calls to `render()`.
- `filterVisibleVideos(scoped)` is the single library filter used by the normal list and return-page lookup. Its results are sorted through `Data.sortVideos` and `sortForReturn`; do not implement a separate filter for return navigation.
- `video-library.js` owns the playback-return intent, saved filter and sort context, and acknowledgement after the target card renders. `VideoLibraryPagination.resolveVideoReturn` takes the grouped results, target ID, and preferred page and returns the destination page plus any series to reveal. The library applies that result to the current list state. The URL and session keys remain compatible with the video player and routing bridge.
- `video-list-route.js.detach()` invalidates startup and removes the list section. The SPA calls it before remounting the video route with `preserveListState` and when leaving the route. The library cancels its page animation on either detach and checks the mounted section before rendering. Its SPA-wide listeners bind once. Already-started data migration and encrypted synchronization can finish off-route.

## Known coupling and deliberate exclusions

- The video list's older edit sheet and dedicated full-page `video-edit-page.js` overlap in UI surface, but they are not safe to delete until all callers and saved guest/Vault data paths are checked.
- `video-routing-fix.js` and `video-thumbnail-time.js` include legacy DOM bridges and storage hooks. The sources still have event/side-effect interactions; removal is a separate targeted migration/test task.
- `recommendations.js` contains a historical reader-only helper chain that names `video-library.js` even though the independent Reader does not own the video list. Static references alone cannot establish whether it still runs on any supported entry: trace actual usage before removing it.
- `video-library.js` still owns direct persistence and edit-sheet events; safe isolation of these must come with shared storage contract tests before altering encrypted sync.
- Tests: `tests/video-data.test.mjs` covers URL consolidation, `tests/video-library-pagination.test.mjs` covers grouped return-page resolution, and `tests/video-library-static.test.mjs` covers storage boundaries. Browser coverage includes `e2e/video-pagination.spec.mjs` for cancellation on detach, along with card design, series, player return, custom properties, and hidden-list search.

## Persistence and concurrent writers

`vault-payload.js` owns the protected key map and Vault representation. The edited routes use `MangaReaderStorage.snapshot` and `writeBatch` for exact-byte preconditions and conditional rollback. The normal property-value editor keeps its normalization and mutations in `video-custom-property-store.js`. The batch writer uses the same origin-wide Web Lock name as that store when the browser supports it. Guest commits use guest-scoped storage.

| Collection | Runtime writers and save behavior |
| --- | --- |
| `videos`, `videoMeta`, `videoFolders` | The list owns legacy-sheet, folder, series, favorite and open actions. The dedicated editor owns add/import, detail edits and confirmed deletion. The edited batch paths check their actual read snapshots, and stale detail forms preserve unsaved input. Dedicated deletes recheck access, then batch the video, metadata and property values with the guarded Vault journal. Folder and legacy-sheet paths still have separate coordination. The bookshelf reads videos for Vault snapshots and no longer rewrites them when saving manga changes. |
| `videoMeta` playback fields | The player checks its title baseline and current video ID before applying a title patch. The legacy routing bridge reads the current map for open counts, playback progress and bookmark enrichment. Thumbnail helpers write thumbnail fields and the legacy bridge preserves selected fields at the Storage API boundary. Shorts writes metrics and cache fields with its timestamp/counter merge. These legacy and Shorts writes still use their own local commit and sync paths. |
| `videoMarkers` | Player controls apply a single addition or ID deletion to the latest marker list under the video/property lock. They check the current video ID at the write, mark additions pending before writing, and journal explicit deletions by marker ID after rechecking access under the local lock. |
| `videoPropertyDefinitions`, `videoPropertyValues` | The property store coordinates settings and video details with its existing lock and checks the raw snapshot again after an asynchronous recipe. The editor only submits changed properties and checks that their values and definitions still match the form's baseline. URL consolidation includes per-video values in its guarded batch. |
| Virtual edit projects and publication | `video-virtual-edit-store.js` manages the revisioned registry inside `videoMeta`. `video-virtual-publish.js` owns split, new, overwrite and restore. It already checks the raw video and meta snapshots before its rollback-capable writes. Both mark pending before local writes and handle cloud failures separately. |
| `videoShortsState` | `video-shorts-state.js` owns queue, reset and progress ordering using generation, revision and timestamp. The profile uses its reset API. It marks pending before account writes and schedules Vault sync. |
| Vault, import and historical paths | `vault-session.js` builds or applies protected snapshots through `vault-payload.js`, journals deletions, and uses the existing encrypted baseline, three-way merge and revision CAS. Backup restores apply through the same payload boundary. `recommendations.js` has historical direct writes to folders and metadata with no live HTML entry reference found. The manga sandbox uses test storage. Browser-only return context, view preferences, thumbnail cache and Shorts audio preferences have separate keys and are outside the four-collection consolidation. |

URL consolidation recomputes after a failed byte-level precondition. The guarded Vault call prepares ciphertext under the account save lock, then takes the local video/property lock for its final access, journal and data checks. A conflict leaves the candidate journal unpublished. A synchronous write failure attempts to restore the original bytes and previous journal and retains the pending marker. Existing journal paths on either the keeper or a duplicate block consolidation until that operation is resolved. The current snapshot determines the removal IDs each time. Numeric IDs in keyed Vault collections are resolved by ID during journal replay.

The account save lock coordinates current clients in the same browser that use the lock. The video/property lock covers URL consolidation, current editor batch and property operations, player title and marker writes, and the list's targeted metadata writes. Other local writers, including older tabs, may bypass it. Snapshot checks detect changes up to the final write checks, and raw-value rollback skips a key when its bytes differ from the batch's writes. LocalStorage offers separate operations per key. A hard crash between journal publication and commit, a rollback storage failure, or a nonparticipating writer between a check and a write can still interrupt this sequence. The encrypted Vault merge, CAS and tombstones coordinate devices through the server, and same-field changes can still require conflict resolution. The remaining local risks include the legacy sheet/folder paths, playback and thumbnail bridges, and full-map restore or publication outside the shared local lock.
