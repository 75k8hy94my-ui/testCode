# 外部ハッシュ形式Readerの境界と技術的制約

> 実装根拠: `reader-runtime.js` の `restoreHashReaderFocus`、`interceptHashChildArrow`、`scheduleHashCorrections`、`inspectHashObservation`、`observeHashFrame`、`destroy`。この文書は現在のコードから確認した事実と、ブラウザの制約を分けて記載する。

## 正規の責任分担

- `reader.html?item=<itemId>` は本棚とは独立した文書。
- `reader-page-source.js` がURL形式とページソースの発見を担当し、`reader-runtime.js` が現在表示するフレーム、要求ページ、埋め込みの制御を担当する。
- `reader-progress-repository.js` が表示確定したページの進捗を保存する。外部iframeが勝手に動いた先のURLを即座に進捗として扱わない。
- `reader-lifecycle.js` / runtimeの `destroy()` がイベント・タイマー・iframe・読み込みを終了する。

## なぜiframe側の矢印キーを常に制御できないか

埋め込み先と親ページが**同一オリジン**なら、子windowの `keydown`、`hashchange`、`popstate` を読んで補正できる。一方、**異なるオリジン**ではブラウザの同一オリジンポリシーにより、親が子の内部URL・イベント・JS状態を自由に読み書きできない。子がフォーカスを得ている間のキーボードイベントも原則として親の `keydown` に届かない。サイト側の明示的な `postMessage` 協力がなければ、完全な双方向同期は保証できない。

現行の実装はこの制約の範囲内で次の方法を使う。

1. 画面外の `#readerKeyboardSink` にフォーカスを戻し、iframe内にキー入力が奪われるのを減らす。ハッシュ形式のReader使用中は80ms間隔のガードが動くが、操作中のツールバーボタン等からはフォーカスを奪わない。
2. 子windowへアクセスできる場合にのみ、左右キーとハッシュ変化を観測して、子サイト固有の左右逆向き処理をReaderの要求ページに合わせる。
3. ページ移動の後、必要な場合に限り `[0,45,150,360]` msの有限回数で目標ハッシュを補正する。タイマーは世代管理で旧操作を無効化し、画面終了でキャンセルする。これは外部サイトの非同期ルーターへの互換措置であり、汎用的な順序調整の推奨ではない。
4. ハッシュ `#1-` は先頭への戻りを示す場合があるが、**同一オリジンで確認できたケースのみ**終端判定に使用する。飛び越した未確認ページの存在を推定しない。
5. 縦スクロールでは、訪問済みiframeを上限付きで保持し、再生成による不要な再読込を抑える。ページ移動要求と表示確定を別管理する。

## 変更時の注意

- 4段階補正を単純な1回の遅延や無制限の再読み込みへ置き換えない。
- iframeに親と同じ権限があると仮定しない。クロスオリジンのアクセス例外は失敗として処理する。
- Readerの最新要求世代・表示確定・進捗永続化を補正処理と混同しない。
- キー補正・スクロールのリスナーを別モジュールへ移す場合、`hashFrameChecks`、タイマー、frameの生成/破棄、ページ要求の世代との閉包結合が大きい。**単なるファイル分割**では危険であり、所有権と取消APIを設計してから実ブラウザで再現検証する。

## 関連テスト

`tests/reader-runtime-boundary.test.mjs` とハッシュReader関連の単体/E2Eテストを使用する。クロスオリジンiframeのURLを読めない条件はテスト用環境でも再現して確認すること。現行のテスト合格だけで外部の全サイトとの互換性を保証するものではない。
