# Vault差分同期・データ保全設計

## 目的

端末の古いVault全体をクラウドへ再送して別端末の変更を消す動作をなくす。同期成功時点の端末基準状態、現在の端末状態、取得したクラウド最新状態から端末の変更部分を確定し、クラウド最新状態へ安全に統合してCAS保存する。既存データ、暗号化、VPNゲート、認証情報、ゲスト動作を維持する。

## 現状と課題

- `vault-session.js` はCAS失敗後にexpected revisionだけを更新し、同じ端末全体payloadを再送している。これは最新revisionを使っていても古い端末全体による上書きになる。
- ローカル変更は`pendingSync`フラグで記録されるが、最後に同期成功したデータ基準は保持されない。
- `vault-payload.js` の正規化は既知のトップレベル項目と一部ネスト項目を再構成するため、将来追加された項目を削除し得る。
- ログアウト、VPN停止時のpending管理、本棚エラー通知、マルチタブロック、動画一括登録、Driveゲスト表示、Vault復元ロールバックなどに個別の欠落がある。
- 現在の作業ツリーにはユーザーの未コミット変更があり、特に動画JSON取込、Shorts、Vault CAS再試行、関連テストが変更されている。これらを作業開始時の基線として保持し、今回の仕様と両立する形で更新する。

## 決定した方式

### 基準状態と操作ID

- 同期成功ごとに、その時点の正規化済みVaultデータを暗号化した基準状態として端末へ保存する。
- 基準状態は現在有効なVaultのAES鍵で暗号化し、ユーザーID、Vault識別情報、暗号方式バージョン、基準revision、暗号文、IVのみを保存する。復号鍵、鍵ラップ、保護対象の平文は保存しない。
- 基準状態とpendingの更新は、localStorageへ一つのレコードとして書き、書き込み失敗時は同期成功扱いにしない。ユーザー切替時はユーザーIDとVault識別子を必ず検査する。
- `pendingSync`は同期要否の表示用とし、変更実体の根拠は基準状態と現在状態の差分にする。既存の書き込み経路を操作ジャーナル対応にすることは有益だが、ジャーナルにない変更も3-way diffで検出する。
- 非可換操作（再生回数等）には一意なoperation IDを付け、Vaultデータの適用済みID集合で重複を抑止する。データ本体と適用済みIDは同じ暗号化payloadに含める。

### 3-way差分統合

変更単位に、安定IDを持つレコード集合、ID付き辞書、フィールド、順序列、カウンター、単一オブジェクト等の型別merge handlerを使う。未知のキーは保持する。すべてのデータを一律にdeep mergeしない。

基準`B`、端末`L`、クラウド`R`の値ごとに次の規則を適用する。

| 条件 | 結果 |
|---|---|
| `L == B` | クラウド値`R`を維持 |
| `R == B` | 端末値`L`を採用 |
| `L == R` | 共通値を採用 |
| 両側が基準から異なる別項目/別プロパティを変更 | 両方を統合 |
| 同じプロパティを両側が異なる値へ変更 | 競合として保存を中断 |
| 片側削除、他側編集 | 競合として保存を中断。削除済みを勝手に復活させない |
| 基準が欠落/復号不可/識別子不一致 | 全体上書きせず停止し、端末状態を維持 |

同一プロパティ競合UIでは対象名、端末値、クラウド値、各更新時点が分かる範囲で提示し、利用者の選択を記録する。競合解決中はpendingを維持する。並び順はID単位の追加・削除・移動情報から統合し、安定した統合ができない場合は明示競合にする。

カウンターは保存済み値の最大値ではなく、一意な増分操作を合算する。再送はoperation IDで冪等化する。

### 同期プロトコル

1. 保存操作前にpendingを耐久化する。端末保存が先に完了しているがpending書き込みが失敗した場合はユーザーに未同期の可能性を通知し、成功表示しない。
2. Vaultが解錠済みでVPN/保護データアクセスが`allowed`であることを再確認する。
3. 同一ユーザーのタブ間排他を取得し、クラウド最新payloadとrevisionを読む。
4. 端末基準を復号し、端末現在payloadとの差分を作る。
5. 3-way統合を実施し、競合があれば書き込まずpendingを維持する。
6. 統合payloadを暗号化し、取得revisionを使いCAS保存する。
7. CAS失敗時は再取得し、必ず新しいクラウドpayloadから手順4以降をやり直す。revisionのみ差し替えて古い暗号文を再送しない。
8. 保存成功後に統合payloadをローカルへ原子的に適用し、同じ更新単位で新基準・revision・pending状態を保存する。
9. 端末状態更新に失敗した場合も未同期扱いを維持し、次回はサーバーと基準を比較して冪等に回復する。
10. タイムアウト後の保存結果不明時は最新revisionを再読込し、operation ID/統合payloadで成功を判定して二重適用を避ける。

ログアウトは可能なら同期をflushする。失敗時はログアウトを中止するか、暗号化された基準と端末状態を保ったままログアウトする選択肢を示す。別アカウントに既存ユーザーのpendingを送らない。鍵/セッションを消去する前にpending状態を確認する。

### 旧版互換性と段階導入

- 既存暗号化envelopeと既知の保存データは読み込める。既存の認証キー、Recovery Key、Passkeyは変更しない。
- 基準メタデータがない既存端末は、ログイン時にクラウドを安全に読み込んで端末へ適用し、その内容を最初の基準とする。読み込み前の端末差分を安全に判定できない場合は同期を停止し、既存端末データのバックアップ/復旧を案内する。
- 旧アプリも同じCAS RPCを使うため、サーバー側でプロトコル世代を識別し、新世代Vaultへ旧payloadが書き込まれる場合は拒否する。クライアント側は明確な更新要求を表示し、pendingを保持する。SQL変更は既存行・RLS・暗号化を維持する追加/制約変更として計画し、適用前に現行Supabase資料と本番プロジェクトのmigration状態を確認する。
- 旧データと未知プロパティを削除しない。`vault-payload.js`は受信payloadの未知トップレベル項目を保持し、既知オブジェクトの正規化でも未知のフィールドを引き継ぐ。明確にsecret/非同期対象の項目だけをallow/deny規則で除外し、`gameSave`を読み書きのround-trip対象として維持する。
- 暗号化済み基準の破損、未知の将来プロトコル、鍵ラップ相違、Vault行消失、revision migration未適用は、復元や新規作成へフォールバックせず停止する。

## 関連信頼性修正の範囲

同期基盤の統合テストに加え、次を修正する。

- `profile-menu.js`と`sync.html`: 未同期確認、同期flush、失敗時の保持/バックアップ導線、誤アカウント送信防止。
- `home-profile-spa.js`とVault書き込みAPI: VPN停止/オフライン中も端末変更をpending化し、許可回復後に安全に再試行。
- `manga-list-route.js`と`manga-list-host-runtime.js`: 空の同期エラー処理をなくし、端末保存とクラウド同期を別状態で通知。
- 動画JSON取込: 動画一覧とmetadataの端末保存をロールバック可能にし、pending登録、同期要求、重複排除、結果件数表示を整える。現在のユーザー未コミット取込コードを基線として保つ。
- 複数タブロック: BroadcastChannel/storage eventでロックを通知し、protected gate、進行中処理、復号済みリソースを停止/消去する。guest動作は変更しない。
- `vault-payload.js`: 手動VPN設定を含む全適用対象をまとめてrollbackし、適用の部分成功を防止。
- `public-drive-gallery.js`: guestで公開画像一覧をVault unlockなしに読み、APIキーを不要に永続保存せず、guest設定をVault同期しない。
- `vault-session.js`読み込みURL: 全HTMLで共通のcache-bustingバージョンを使い、リリース時に一括更新。
- 同期対象全体をgameを除いて監査し、今回のデータ保全に直接関わる取りこぼしを修正する。gameコードには手を加えず、gameSaveのデータ互換性を検証する。

## テスト

同期merge関数をDOM/ネットワークから分離し、Node標準テストでB/L/Rの結果と競合分類を検証する。複数端末を独立fixtureとして用意し、CAS競合、同時追加、プロパティ単位の変更、削除対編集、増分操作重複、タイムアウト後再読込、オフライン復帰、マルチタブロック、旧protocol書込拒否を検証する。

端末保存失敗、容量不足、暗号化/復号失敗、HTTP 5xx、期限切れ、Vault消失、古いmeta、部分適用、ログアウト時未同期、復元失敗をfault injectionで確認する。payload round-tripには未知プロパティ、gameSave、Drive暗号設定、手動VPN設定を含める。実データではなくmockと専用fixtureを用いる。

関連UI変更は実ブラウザでも、保護データを破壊しないguest/mockの画面状態を確認する。リポジトリ必須チェックは`npm test`、`npm run verify:static`、`git diff --check`。SupabaseのSQL検証は本番データを変更しない開発ブランチ/fixtureで行う。

## 公開とデプロイ

既存Supabaseスキーマ、RLS、暗号化方式を維持する。SQL migrationが必要なら、保存済みpayloadを更新・削除する移行は行わず、適用可能な追加migrationにする。PRに移行手順と旧版クライアントの挙動を記載する。

GitHub Pagesの公開経路を早期に確認し、PRをmainへ反映した後、意図したmain commitのPages deploymentが開始したことをGitHub Actionsで確認する。開始の証跡がない限り完了としない。

## 受け入れ条件

1. 同じVault基準から始め、Aが漫画Xを追加して同期した後、古いBが動画Yを追加して同期してもクラウドにXとYが残る。
2. 同じ動画の異なるプロパティ編集は両方残る。
3. 同じプロパティの異なる編集、削除対編集は保存前に競合になり、どちらの値も失われない。
4. CAS失敗後は最新データから再mergeする。
5. 失敗、ロック、VPN停止、ログアウト試行でpendingまたは暗号化復旧情報を無断消去しない。
6. 未知項目、既存データ、ゲーム保存がround-tripする。
7. PR merge後に該当main commitのPages deployment開始を確認する。
